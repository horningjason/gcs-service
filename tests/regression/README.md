# GCS Regression Test Harness

Golden-file regression suite, structured after lvf-service's
`tests/regression/` — a real service, real data, a frozen baseline, and a
runner that semantically diffs against it. Adapted from LOST's XML-in/XML-out
shape to the GCS's two response formats across four conversion endpoints: the
strict resources answer 200 with XML wrapping XML (`GeodeticData` /
`CivicAddress` carrying the PIDF-LO in CDATA — decision 116), the enhanced
resources with JSON wrapping XML, and every non-200 with JSON. `harness.py`'s
`parse_outcome()` branches on the response content type and reduces all of
them to one comparable shape.

## Philosophy: seed once, never rebuild

Golden files represent **known-good behavior locked in at a specific point in
time**. Once seeded, they must not be regenerated casually — if you do, any
bug present at seed time becomes the new baseline and the suite stops
catching it. Treat golden files like a signed test report: change them only
with intent and review.

This suite runs against the **real engine**, in-process — no ASGI app, no
TestClient, no port, matching lvf-service's `tests/regression/runner.py`
calling `handle_find_service(xml_bytes)` directly rather than going through
its FastAPI app. `harness.py`'s `initialize()` is
`src/app/lifecycle.py`'s own documented "synchronous startup for tests and
tooling that do not run the ASGI lifespan": it loads the schema, registers
`src/engine/scoring.py`'s real (if still data-unproven — see the root
CLAUDE.md's "Tuning constants that are strawmen" section) scoring functions,
and loads the real `data/data.gpkg`, without starting the NTP client, the
SIP listener, or the GIS watcher thread. Each `_dispatch_*` function in
`harness.py` then calls the same plain functions the real route handlers
wrap — `admit()`, `conversion.geocode()` / `conversion.reverse_geocode()`,
`response_json.*`, `status.*` — directly. That is deliberately different
from `tests/conformance/`, which injects trivial scorers and a two-record
in-memory GIS to isolate wire/admission/assembly logic from the scoring
formula. This suite exists to catch the opposite class of regression: what
happens when the real formula runs against tens of thousands of real,
messy, real-world records. It already caught one — see below.

## Nothing here is hardcoded address data

Unlike lvf-service's `tests/*.xml`, the request bodies under `inputs/` are
**not committed** (`.gitignore` already excluded `tests/regression/inputs/`
and `tests/regression/golden/` before this suite existed — "may contain real
address data"). `build_inputs.py` *is* committed, and contains no address
data itself: it discovers fixtures from whatever GeoPackage
`GCS_GPKG_PATH` points at by the *shape* of a condition (an exact address
point, an ambiguous same-address pair, a rural RoadCenterLine segment with no
SiteStructureAddressPoint anywhere near it, ...), never by name. Point it at
a different jurisdiction's export and it produces a different, still
sensible, fixture set.

```
tests/regression/
  manifest.py        Committed. Test ID -> endpoint + transport. No address data.
  build_inputs.py     Committed. Discovers fixtures from data.gpkg -> inputs/*.xml.
  harness.py          Committed. Boots the real service; dispatch + semantic reduction + diff.
  seed.py             Committed. One-time seeder (run once per new test, do not commit output).
  runner.py           Committed. Regression runner (run any time).
  inputs/              Gitignored. Generated by build_inputs.py.
  golden/               Gitignored. Generated by seed.py.
```

## Running the tests

```bash
python -m tests.regression.runner                          # run all
python -m tests.regression.runner --test FWD-GAP-HNO-001    # run one
```

First run on a fresh checkout builds `inputs/` from `data/data.gpkg`
automatically (if empty), then seeds `golden/` automatically (if empty), then
runs. Exit code is `0` if everything passes, `1` on any failure, error, or
missing golden file.

## Seeding golden files (run once, or after a reviewed behavior change)

```bash
python -m tests.regression.build_inputs                      # (re)discover fixtures — idempotent
python -m tests.regression.seed                               # seed all, skip existing
python -m tests.regression.seed --force                       # overwrite all
python -m tests.regression.seed --force FWD-GAP-HNO-001       # overwrite one by ID
```

`seed.py` refuses to overwrite an existing golden file unless `--force` is
passed. **Never `--force` the whole suite as a way to silence a failure** —
diagnose it first. If a deliberate algorithm or data change produces
different correct answers, review the diff, then `--force` only the affected
IDs.

## Adding a new test case

1. Add a `Case(...)` to `manifest.py` with a new ID (`PREFIX-MNEMONIC-NNN`)
   and target endpoint.
2. Add the fixture's discovery + `_write(...)` call to `build_inputs.py`'s
   `build()`, using `Fixtures`' existing lookups or a new condition-based one
   — never a literal address.
3. `python -m tests.regression.build_inputs` to generate the new input.
4. Inspect `tests/regression/inputs/<ID>.xml` — read the header comment it
   wrote, sanity-check the real record it picked.
5. `python -m tests.regression.seed --force <ID>` and inspect
   `tests/regression/golden/<ID>.golden.json` before trusting it. Real data
   does not always do what you expect it to (again, see below) — confirm the
   captured outcome is actually correct, not just plausible, before treating
   it as a baseline.

## What the runner compares

Semantic (parsed JSON + embedded XML), not a byte diff, positional on
candidate lists (rank order is meaningful — §10.3's order is preserved
exactly, never re-sorted). Per response:

- **status code** — the closed set (§8.4, §12.3): 200/307/454/468/469
- **454** — the `reason` body field
- **200 strict** — the civic fields and/or geodetic shape (Point,
  LineString, or Circle — §6.3's merge/averaging answer) embedded in
  `pidfLoGeo`/`pidfLoAddress`, plus the RFC 7459 `confidence` element where
  present
- **200 enhanced** — every candidate's quality fields (matchScore,
  locationType, confidence, matchType, matchScoreBreakdown), reverse-only
  fields (distanceMeters, contained, houseNumberSynthesised), and the same
  embedded-document reduction as the strict case, plus `locationCount` and
  `droppedElements`

## Real data does not do what you expect it to

Three fixtures in this suite exist in their current form only because the
first version's *assumption* about what real data would do was wrong, and
the seeded golden file said so. Recorded here so the next person adding a
fixture doesn't repeat the exploration:

- **A no-house-number query almost never degrades cleanly to a rung-3
  street-level LineString on real data**, even though that is exactly what
  the synthetic unit test in `tests/conformance/test_conversion_http.py`
  demonstrates. §6.2 has no progressive filter: dropping the house number
  doesn't narrow the candidate set, so on any real street that has address
  points provisioned on it, *every one of them* still scores 100 (decision
  66 — `Add_Number` isn't even a compared term once unpopulated) and rung-1
  always outranks rung-3 (decision 70). A real street with more than a
  couple of houses spans well past `GCS_AMBIGUITY_TOLERANCE_M`, so the
  honest outcome is usually 468, not a clean line. `FWD-STREET-ONLY-001` and
  `FWD-DROPPED-HNO-*-001` therefore deliberately use
  `Fixtures.rcl_only_street()` — a real RoadCenterLine street with *zero*
  SiteStructureAddressPoints anywhere on it — which is the only condition
  that reliably produces the clean single-LineString answer on real data.
- **Decision 82's deliberate absence of an A1/Country gate means an
  "ambiguous pair" query can pull in far more than the two candidates you
  picked it for.** `FWD-AMBIG-MERGE-001` was built around a real two-unit
  address, but on the full statewide dataset, other addresses sharing the
  same house number and a fuzzy-similar street name elsewhere in the state
  also clear `GCS_MIN_MATCH_SCORE` and join the candidate set — so the
  strict answer is 468 (ambiguity beyond tolerance), not the tidy centroid
  merge the fixture's name suggests. Supplying the disambiguating
  `UnitValue` (`FWD-UNIT-DISAMBIG-001`) doesn't fix this either: decision
  75's unit gate excludes only records with a *differing* `UnitValue`
  populated, and the far-flung collisions typically have none to differ on.
  Both outcomes are captured as they really are, with the mechanism
  explained in each fixture's header comment.
- **A rung-2 interpolation candidate can legitimately compute
  `match_score == 100.00000000000001`.** The first seeding run crashed with
  an uncaught `ValueError` from `MatchQuality.__post_init__`'s strict
  `[0, 100]` range check — a real, address-triggered production bug this
  suite found on its first run, not a synthetic edge case. `src/engine/
  scoring.py`'s `_weighted_average()` now clamps its result; see that
  function's docstring for the float-non-associativity explanation.
